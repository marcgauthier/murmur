# Schema and migrations

Schema restrictions, stable identities, concurrent additive migrations, and local-only objects.

Current applications define records with `Config.Models` or `Config.Tables` and use the
managed RIME API. `Open` rejects SQL-only `Schema.Tables` configurations. The
old SQL restrictions below are historical; no SQL schema or statement runtime
ships in production. The
automatic model registration and row identities are documented in
[the model API guide](model-api.md). The current record descriptors, field IDs, codecs, presence rules, and migration

## 6. Schema Rules for Version 1

Masterless SQL replication becomes dramatically harder when arbitrary relational constraints are allowed.

Version 1 should deliberately support a constrained replicated schema.

### Required rules

Every replicated table must have:

- An explicit nonzero `RowID` primary key supplied by the application or generated by model insertion (UUIDv5 from a business key, otherwise UUIDv4).
- Primary key type compatible with a 16-byte UUID.
- Primary keys are immutable; no local sequence or implicit row identity is used.
- Stable column identities.
- A schema version known to the package.

Recommended:

```sql
CREATE TABLE contacts (
    id BLOB(16) PRIMARY KEY NOT NULL,
    name TEXT,
    phone TEXT,
    email TEXT
);
```

### Initially disallow or restrict

- `AUTOINCREMENT` on replicated tables.
- Replication based on implicit `rowid`.
- Secondary `UNIQUE` constraints and explicit `CREATE UNIQUE INDEX` on managed tables. Only the index required to enforce the declared primary key is allowed.
- Cross-column `CHECK` constraints. A permitted check must reference only the column on which it is declared, for example `status TEXT CHECK (status IN ('active', 'disabled'))`.
- Direct application writes to replication metadata tables.
- Replication of virtual tables.
- Replication of FTS internal tables.
- Arbitrary DDL through normal `Exec`.
- Schema changes independently performed on disconnected nodes.

### Foreign keys

Foreign keys may be useful locally, but multi-master/offline operation means remote changes can arrive out of order.

Foreign-key declarations and normal JOIN queries are allowed, but enforcement must remain disabled on every managed SQL connection, including local writes, remote apply, and rebuild. Do not rely on cascading deletes/updates; applications must express those mutations explicitly. Out-of-order replication must allow a child to arrive before its parent.

### Validation and index creation

The SQL validation rules and DDL examples in this section are retained only as
historical design context. Production callers define stable typed descriptors
through `Model[T]` and `Config.Tables`; RIME registers the corresponding
primary keys and supported indexes. Unsupported distributed constraints are
rejected during typed schema compilation.

### Wire-frontend enforcement

> **Planned (deferred):** The standalone `murmurd` daemon will add MySQL and
> PostgreSQL wire frontends. The rules below describe their intended behavior.
> The embedded engine already enforces the same invariants independently
> (see embedded-engine enforcement above).

When the wire frontends exist, they will enforce this section before anything
commits, so clients that assume a full MySQL/PostgreSQL dialect fail closed with
an explicit Murmur reason instead of a confusing engine error or a half-created
table:

- Secondary `UNIQUE` constraints and `CREATE UNIQUE INDEX` are rejected on both frontends: Murmur replicates only the primary-key index. Typed RIME indexes are declared in Go record definitions and remain local to each materializer.
- `CREATE TABLE` without exactly one `PRIMARY KEY`, or with a key that is not the single `id` blob column, is rejected. The wires normalize a bare `PRIMARY KEY` to a stored `PRIMARY KEY NOT NULL`; `Migrate`/`BuildRegistry` still rejects any nullable or non-blob key that reaches it.
- Column and table options Murmur does not model — `DEFAULT`, `AUTO_INCREMENT`/`SERIAL` (column or table option), generated columns, `CHECK`, `FOREIGN KEY`/`REFERENCES` — are rejected rather than silently dropped. Single-column checks and unenforced foreign-key declarations remain tolerated at the embedded-engine level only; the wires stay a strict subset.
- A `UNIQUE` keyword merged into the MySQL `PRIMARY KEY` column itself is redundant and normalized away; no secondary index exists afterwards. Every other rejected statement leaves no residue: no table, no schema-epoch advance, no sidecar change.

The MySQL side will guard at pre-analyze time (its engine would otherwise commit the table before creating indexes); the PostgreSQL side will guard in its strict `CREATE TABLE` parser.

### Primary-key stability and column resolution

Primary-key columns and their identities are immutable once a table participates in replication. Changing them requires explicit teardown and rebuild of that table's replica state; ordinary migrations must reject the change.

Ordinary columns, including integers, use per-column last-writer-wins resolution. Concurrent arithmetic updates do not implement distributed counters: the winning value replaces the other value. Specialized counters require a separately designed replication type and are outside v1.

### Schema ownership & State-Based Synchronization

The cluster uses **State-Based Full Schema Synchronization** rather than streaming incremental DDL events.

Each node persists its complete, authoritative schema manifest:

```go
type SchemaManifest struct {
    Version       uint64        // Authored revisions advance; compatible merge epochs follow ancestry
    CreatedOnNode NodeID        // Node identity that authored this schema epoch
    TimeCreated   uint64        // HLC timestamp when epoch was authored
    Hash          [32]byte      // Canonical SHA-256 hash of tables, columns, and types
    Tables        []TableSchema // Full table and column definitions
    Parents       [][32]byte    // Canonical parent revision/merge identities
}
```

The package stores this manifest in Spool under prefix `0x06`.

SMF1 is the original scalar encoding, SMF2 adds merge-policy bytes, and SMF3
adds rich record descriptors when a table carries a
Go `RecordDescriptor`: its canonical bytes participate in the content hash and
are persisted alongside the scalar table envelope. Schema union and ancestry
checks allow recursively additive stable field IDs and deterministic unions of
concurrent additions. Existing field types, codec identities, merge semantics,
table IDs and primary keys remain immutable; incompatible changes are rejected.

#### Node-Level Sync Policy (`AcceptRemoteSchema`)

Each node controls whether it permits peers to upgrade its local schema:

```go
type SchemaConfig struct {
    Version            uint64
    Tables             []schema.TableSchema
    AcceptRemoteSchema *bool // nil defaults to true
}
```

- **`AcceptRemoteSchema = true` (Default):**
  When connecting to a peer with a different schema, the node downloads the full manifest and ancestry, validates compatibility, and adopts a compatible descendant or computes the canonical additive union from [Section 50](schema.md#50-schema-migration-strategy). Apply missing additive DDL and persist the accepted manifest before acknowledging schema compatibility.
- **`AcceptRemoteSchema = false` (Strict Enterprise Control):**
  The node refuses remote schema changes, aborts the handshake with `ErrSchemaMismatch`, and halts replication with that peer until its local configuration is updated.

Data replication is strictly gated: peers only stream data mutations after verifying both nodes share the identical canonical schema version and hash. Conflicting definitions fail closed; strict nodes do not silently adopt or acknowledge unknown schema data.

## 7. Stable Table and Column IDs

Do not replicate table and column names on every mutation.

Create a schema registry.

Example:

```text
contacts       -> table_id 17
contacts.id    -> column_id 1
contacts.name  -> column_id 2
contacts.phone -> column_id 3
contacts.email -> column_id 4
```

Use deterministic IDs when possible.

One option:

```text
table ID  = stable 32-bit ID stored in schema manifest
column ID = stable 32-bit ID stored in schema manifest
```

Do not regenerate IDs based only on ordinal position because adding/reordering columns would break compatibility.

Schema manifest example:

```go
type TableSchema struct {
    ID      uint32
    Name    string
    PK      uint32
    Columns []ColumnSchema
}

type ColumnSchema struct {
    ID       uint32
    Name     string
    Type     ColumnType
    Nullable bool
}
```

Store a canonical serialization and SHA-256 hash.

## 50. Schema Migration Strategy

Rather than streaming incremental DDL scripts, the cluster uses **State-Based Full Schema Synchronization**:

Each schema upgrade produces a new, immutable `SchemaManifest` with:
- Monotonically bumped `Version` (`uint64`)
- Authoring `CreatedOnNode` (`NodeID`)
- Authoring `TimeCreated` (`uint64` HLC timestamp)
- Canonical `Hash` (`[32]byte`)
- Complete table and column schemas
- Canonical parent revision identities and persisted ancestry sufficient to deduplicate compatible merges

### Legacy SQL Schema Migration (retired)

This path is no longer accepted by `Open`; the SQL migration API was removed.
The following describes the retired implementation for historical reference.

Applications initiate an upgrade on any authorized node via the package API:

```go
// Retired API; use MigrateRecords with complete typed TableDefinition values.
```

The node:
1. Validates [Section 6](schema.md#6-schema-rules-for-version-1) restrictions (UUID primary keys, no autoincrement, no duplicate names).
2. Generates deterministic IDs for newly added tables and columns.
3. Bumps `Version`, captures `TimeCreated` (HLC), derives `CreatedOnNode`, and computes canonical `Hash`.
4. Records the canonical parent identity and validates the full declaration against current authoritative schema, including same-name definitions and ID collisions.
5. Persists the new manifest/ancestry atomically in Spool under `0x06`; RIME indexes are rebuilt from records and migration publication follows the materialization-generation protocol.
6. Applies missing additive DDL and updates local `schema.Registry`; block writes/replication during publication. A post-Spool DDL failure marks the materializer dirty and requires rebuild before readiness.
7. Future replication handshakes advertise the version/hash and exchange manifests/ancestry before data mutations.

### Managed Typed Schema Migration

Applications using `Config.Tables` evolve the complete Go table set with
`DB.MigrateRecords(ctx, definitions)`. The operation accepts additive typed
schema changes and rejects drops or incompatible stable IDs, types, and merge
policies. It durably stores the new manifest in Spool before rebuilding and
publishing the private RIME materializer, then refreshes replication identity
and typed subscriptions.

The schema-store boundary is crash-safe. A process death before manifest store
reopens on the prior epoch; a death after the store reopens on the new epoch
when the application supplies the matching new `Config.Tables` declarations.
The root typed schema crash test exercises both boundaries in child processes
using encrypted on-disk Spool. The [`migration-crash` live gate](../tests-live/migration-crash/README.md)
injects process exit immediately before and after manifest storage while the
migrating peer is isolated from two epoch-1 peers. It verifies restart at the
correct epoch, record recovery, peer adoption, rebind and convergence. The
concurrent migration live gate separately checks writes, epoch adoption and
convergence during simultaneous migrations.

### Additive vs. Destructive Schema Rules

1. **Managed additive operations (allowed):**
   - Add a table through a complete `Config.Tables` definition.
   - Add fields or indexes with stable IDs through `DB.MigrateRecords`.
   - Peers with `AcceptRemoteSchema = true` adopt compatible additive manifests and continue replication through RIME.

2. **Destructive Operations (Restricted/Coordinated):**
   - `DROP TABLE`, `DROP COLUMN`, or altering primary keys.
   - Dropping a column while disconnected nodes continue writing to it produces silent data corruption or replication gaps.
   - Destructive changes cannot be automated in masterless peer-to-peer topology; they require coordinated cluster maintenance.

### Handling Disconnected Concurrent Migrations

Preserve multi-author additive migration; do not silently select a winner for incompatible definitions by timestamp or NodeID. Concurrent branches may have equal or different epoch numbers, so compare ancestry and declarations as well as numeric versions.

- Canonicalize tables, columns, indexes, defaults, and supported constraints by stable identities and normalized definitions before hashing. Shared declarations must be identical; distinct compatible additions are unioned. Same-name/different-type, default, nullability, primary-key, or index-definition conflicts fail with `ErrSchemaMismatch` identifying the object. Detect numeric ID/hash collisions between different canonical names instead of assuming deterministic derivation makes collisions impossible. Nothing is applied/acknowledged from an incompatible branch until the application explicitly supplies a compatible resolution.
- Persist immutable authored revisions and parent identities. An authored revision has epoch `1 + max(parent epochs)` and retains its authoring time/NodeID. For a compatible concurrent merge, flatten synthetic merges into a sorted frontier of authored revisions and remove ancestors already covered by a frontier descendant. Derive the synthetic merge identity from that frontier and canonical union, its epoch as `1 + max(frontier epochs)`, and author/time fields from the greatest frontier `(epoch, TimeCreated, CreatedOnNode)` tuple. Do not use receive time or the merging node's clock/identity.
- Reuse the persisted result for a known frontier. If a received manifest is a compatible descendant covering the local frontier, adopt it without creating another merge. If definitions/frontier already match, do nothing. Repeated A/B exchanges and different merge arrival orders must produce the same result, without repeatedly applying `max(localVersion, remoteVersion) + 1`.
- A merged epoch need not uniquely identify schema content: independent frontiers may produce the same number. Its canonical hash/ancestry disambiguate it, including equal-epoch/different-hash handshakes. Exchange missing ancestry incrementally with bounds; if the peer cannot provide sufficient ancestry to prove a safe union, reject/defer synchronization rather than guessing.
- Publish only compatible schema and rebuild/materialize before data replication. Preserve local additions when receiving a numerically higher concurrent branch. Keep destructive operations coordinated and outside automatic union.

### Forward-Compatible Schema Evolution & Node Policy

In rolling cluster upgrades:
1. **Nodes with `AcceptRemoteSchema = true` (Default):**
   - Adopt a compatible descendant or canonical union, apply missing tables/columns, and then replicate data under the agreed canonical schema identity.
2. **Nodes with `AcceptRemoteSchema = false`:**
   - Refuse the peer manifest, signal `ErrSchemaMismatch`, and pause replication with that peer until local configuration is explicitly updated.
3. **Unknown or Incompatible Mutation Schema:**
   - Reject/defer the transaction and request schema synchronization before authoritative apply. Do not advance its receive watermark or partially materialize known columns. Strict nodes continue refusing the transaction until explicitly upgraded. After compatible schema publication, retry the complete transaction with its original identity.

Retained transactions from a validated compatible ancestor schema remain applicable after an additive upgrade: resolve their original column identities using persisted ancestry and apply the complete original batch under the current compatible schema. Preserve its original schema provenance, TxID, sequence, and payload digest; do not rewrite historical payloads just to match the current epoch. If ancestry cannot prove compatibility, defer/reject without applied acknowledgement.

## 51. Local-Only Objects

In native typed mode, `RecordOptions.Scope` marks tables as replicated
(default), persistent node-local (`TableScopeNodeLocal`), or ephemeral
(`TableScopeEphemeral`). Persistent node-local LWW cells use their own encrypted
Spool namespace and are absent from the cluster manifest, replication log, and
snapshots. Their stable table and field IDs are supplied by application code.
Ephemeral LWW rows exist only in the in-memory RIME materializer and reset on
reopen. A write transaction cannot mix an ephemeral table with any durable
table. Node-local tables cannot be used by typed bridge imports or exports.

Murmur no longer exposes SQL `LocalDDL` configuration. Local indexes are
declared with the Go record definition; views are application Go queries or
RIME maintained views. The SQL-backed materializer and its private DDL helpers
were removed in Phase 6.

Allow schema declarations to mark:

```text
replicated table
local table
local index
local view
FTS index
```

Replicated cells enter the cluster-visible Spool namespace and replication
snapshots. Persistent typed node-local cells also enter encrypted Spool, but
use a separate namespace that is never exported or replicated. Ephemeral typed
rows remain only in memory.

Examples of local-only objects:

```text
views
FTS virtual tables
temporary tables
query caches
statistics
application-specific search indexes
```

This keeps replication lean.

Murmur no longer persists SQL views. Applications can express reusable views
as Go query functions over typed tables; standalone RIME users can use its
maintained-view API. Neither form enters replicated schema or Spool state.

Reopening a database preserves declaration column order. The stored
manifest encoding sorts columns by hash-derived ID, so the reopen path
keeps the config-built registry (whose hash match proves identical IDs,
names, and types) instead of rebuilding from the manifest: rebuilding
from the manifest would permute physical column order on every reopen
whenever ID order differs from declaration order.

Long-lived applications obtain the reopen declaration from
`DB.LiveSchema`, which exports the current epoch plus the resolved
table declaration; persisting that export after each migration and
before shutdown keeps restarts exact across replicated schema
adoptions. Call `DB.LiveSchema` after each `DB.MigrateRecords` and before
`DB.Close`, and pass the saved declaration back into `SchemaConfig` on
the next `Open` call.
